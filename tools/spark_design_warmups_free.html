Spark Design Warm-ups

Five original interview sketches with short worked answers (PySpark-style mental models). Not a company interview bank and not employer material — written for learning. Assume Spark 3.x with Adaptive Query Execution available unless noted. Attempt cold, then tap Reveal.

Practice context (fictional)

Made-up “NadiHaul” logistics lake — practice only, not a real production system.

Daily parcel scan events → bronze Parquet → silver cleansed → gold aggregates for ops dashboards. Cluster: modest (8–32 executors). Prefer honest trade-offs over buzzwords.
SP1 · Easy

Tiny files after a nightly landing

Bronze lands ~40k tiny Parquet files every night (one micro-batch file per minute per hub). Silver jobs crawl. What do you change on write, and what do you say in the interview? 

# Prefer fewer, larger files on write
(
  bronze
  .repartition(32)          # or coalesce after a reduce; tune to ~128–512 MB files
  .write.mode("append")
  .option("maxRecordsPerFile", 2_000_000)
  .partitionBy("event_date")
  .parquet("s3://lake/nadihaul/bronze/scans")
)

# Later: OPTIMIZE / rewrite compaction job for existing tiny files
# Interview line: “Small files kill listing + task scheduling; I size files on write and compact on a schedule.”

Why. Tiny-file hell is a metastore + scheduler tax, not a “buy bigger cluster” problem. Target file size, not file count.

SP2 · Easy/Med

cache vs checkpoint (lineage pain)

A long silver pipeline fails after 90 minutes. Restart rebuilds the whole DAG from bronze. When do you cache/persist, and when do you checkpoint instead? 

# Reuse within ONE job / interactive session → persist
cleaned = silver.transform(...).persist(StorageLevel.MEMORY_AND_DISK)
cleaned.count()  # materialize before branching

# Break lineage across retries / very deep DAGs → checkpoint
spark.sparkContext.setCheckpointDir("s3://lake/tmp/checkpoints")
stable = cleaned.checkpoint()   # truncates lineage; writes to durable path

# Interview line: “cache/persist = reuse in this JVM; checkpoint = cut lineage for recovery.”

Why. Persist keeps lineage (cheap reuse, costly rebuild). Checkpoint pays write cost to make restarts sane. Don’t checkpoint every step.

SP3 · Med

Python UDF tax

Someone added a Python UDF that parses a messy address string on 80 GB of events. Job is 6× slower. How do you talk about the cost, and what do you try first? 

# Prefer built-ins / Spark SQL expressions / higher-order functions
fixed = (
  events
  .withColumn("city", F.element_at(F.split(F.col("address"), ","), -2))
  .withColumn("pin", F.regexp_extract("address", r"(\d{6})", 1))
)

# If you must UDF: pandas_udf (vectorized) beats row-at-a-time Python UDF
# Last resort: rewrite hot path in Scala/Java UDF or push to preprocessing

# Interview line: “Row Python UDFs break Catalyst + Arrow benefits; I measure with/without and replace with expressions first.”

Why. UDFs are an escape hatch. Interviewers want you to name serialization + lost optimizer pushdowns, then show a concrete rewrite.

SP4 · Med

Reading nested JSON without schema roulette

Ops drops gzipped JSON events with nested device and metrics[]. Inferring schema every run is flaky and slow. Design the read path. 

schema = StructType([
  StructField("event_id", StringType()),
  StructField("event_at", TimestampType()),
  StructField("device", StructType([
    StructField("hub_id", StringType()),
    StructField("fw", StringType()),
  ])),
  StructField("metrics", ArrayType(StructType([
    StructField("name", StringType()),
    StructField("value", DoubleType()),
  ]))),
])

raw = (
  spark.read
  .schema(schema)                 # explicit schema — no inferSchema on prod paths
  .option("mode", "PERMISSIVE")   # or FAILFAST in strict CI
  .option("columnNameOfCorruptRecord", "_corrupt")
  .json("s3://landing/nadihaul/events/")
)

# Explode metrics later in silver; quarantine _corrupt rows
# Interview line: “Prod reads ship a versioned schema; inference is for exploration only.”

Why. Schema-on-read still needs a contract. Explicit schema + corrupt-record column beats silent type drift.

SP5 · Med

AQE on, but the plan still looks wrong

Adaptive Query Execution is enabled. A join still shuffles a small dimension table. What do you check in the Spark UI, and what knobs do you change deliberately? 

# Confirm in UI: SQL tab → node type (BroadcastHashJoin vs SortMergeJoin)
# Stats: sizeInBytes on the build side; skewed partition indicators

# Deliberate broadcast for a known small dim
dim = F.broadcast(hubs)   # or raise spark.sql.autoBroadcastJoinThreshold carefully
fact.join(dim, "hub_id")

# AQE helpers (already on in many 3.x defaults):
# spark.sql.adaptive.enabled=true
# spark.sql.adaptive.skewJoin.enabled=true
# coalesce post-shuffle partitions when too many tiny tasks

# Interview line: “I verify the physical plan, not the config dump; AQE helps but doesn’t replace size judgment.”

Why. Config folklore ≠ proof. UI join operator + approximate sizes beat guessing. Broadcast only when the build side truly fits.
