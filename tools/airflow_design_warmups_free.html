Airflow Design Warm-ups

Five original interview sketches with short worked answers (Airflow 2.x mental models). Not a company interview bank and not employer material — written for learning. Assume Airflow 2.x with a Scheduler + Triggerer unless noted. Attempt cold, then tap Reveal.

Practice context (fictional)

Made-up “NadiHaul” logistics platform — practice only, not a real production system.

Hub scan landings → warehouse loads → ops dashboards. Shared MWAA-/Astro-style cluster with other teams’ DAGs. Prefer honest trade-offs over buzzwords.
AF1 · Easy/Med

catchup=True after weeks offline

A daily DAG was paused for 3 weeks. Someone unpauses it with catchup=True and start_date still at the old value. What happens next, and how do you recover safely? 

# Scheduler will backfill ~21 daily runs in catch-up order
# Risk: thundering herd on warehouse / API + surprise bill + SLA noise

# Safe recovery pattern
# 1) Pause again immediately if already exploding
# 2) Set catchup=False (or keep True but raise start_date to "today")
# 3) Clear only the runs you intentionally need; prefer a one-off backfill DAG
#    with bounded data intervals + max_active_runs=1
# 4) Confirm logical date vs data interval before clearing

# Interview line: “catchup=True is a time machine — I treat unpausing as a capacity event.”

Why. Catch-up is useful for intentional historical loads; accidental unpause after downtime is a classic cluster meltdown story. Name the herd, then the bounded fix.

AF2 · Med

Pools vs starving other DAGs

Heavy extract tasks (API + warehouse unload) take most worker slots. Other teams’ short DAGs queue for hours. How do you use pools / concurrency so heavy work can’t starve everything? 

# Create a pool for the expensive path (UI / CLI)
# airflow pools set nadihaul_extract 4 "API + unload slots"

# Task
extract = PythonOperator(
    task_id="extract_hub_scans",
    python_callable=...,
    pool="nadihaul_extract",
    priority_weight=5,           # optional: prefer critical extracts inside the pool
)

# Also cap the DAG itself
with DAG(
    ...,
    max_active_runs=2,
    max_active_tasks=8,          # Airflow 2.2+ DAG-level task concurrency
):
    ...

# Interview line: “Pools budget scarce external capacity; DAG max_active_* budgets my own fan-out.”

Why. Default shared slots = tragedy of the commons. Interviewers want you to name pool slots for the scarce resource (API QPS / warehouse slots), not only “buy more workers.”

AF3 · Med

Deferrable sensor vs poking FileSensor

A classic FileSensor with poke_interval=60 waits up to 6 hours for a late hub drop. Worker slots sit occupied. What do you change, and what component must be running? 

# Prefer a deferrable sensor (releases the worker slot while waiting)
wait = FileSensorAsync(          # or FileSensor(..., deferrable=True) on versions that support it
    task_id="wait_hub_drop",
    filepath="s3://landing/nadihaul/{{ ds }}/_SUCCESS",
    poke_interval=60,
    timeout=6 * 3600,
)

# Requires the Triggerer process/service healthy
# airflow components: scheduler + webserver + workers + triggerer

# Interview line: “Poke sensors rent a worker; deferrable sensors rent a Triggerer wakeup.”

Why. Idle poke loops waste concurrency. Deferrable sensors free workers until the Triggerer fires. Always mention the Triggerer as the missing piece in many “we enabled async sensors but nothing deferred” stories.

AF4 · Med

Dynamic task mapping over files

Some nights you get 3 hub files; some nights 40. A static DAG with 40 parallel tasks looks silly on quiet nights and fails when night 41 appears. How do you map tasks over a discovered list? 

@task
def list_hub_files(data_interval_start=None) -> list[str]:
    # return zero-or-more object keys for that interval
    return s3.list_keys(prefix=f"hubs/{data_interval_start:%Y-%m-%d}/")

@task
def load_one(key: str) -> str:
    return load_to_warehouse(key)

with DAG(..., max_active_tasks=12):
    keys = list_hub_files()
    # Dynamic Task Mapping (Airflow 2.3+)
    results = load_one.expand(key=keys)
    # empty list → zero mapped instances (no-op), not a hard fail

# Interview line: “I map over the discovered set; I don’t hard-code N parallel tasks for a variable N.”

Why. Static N is a maintenance trap. Mapping scales with the list; pair it with max_active_tasks / pools so a 200-file night doesn’t melt the cluster.

AF5 · Med

Dataset / TriggerDagRun decoupling

Producer DAG lands silver Parquet; three consumer DAGs (ops KPI, finance extract, ML features) all used to hard-code ExternalTaskSensor on the producer’s task_id. Refactors keep breaking sensors. How do you decouple with Datasets or TriggerDagRun? 

# Option A — Data-aware scheduling (Airflow 2.4+ Datasets)
SILVER_SCANS = Dataset("s3://lake/nadihaul/silver/scans")

# producer
@task(outlets=[SILVER_SCANS])
def write_silver(): ...

# consumer DAG: schedule=[SILVER_SCANS]  # runs when outlet updates
# Consumers no longer know producer task_ids

# Option B — explicit TriggerDagRunOperator when you need params / one-shot
trigger = TriggerDagRunOperator(
    task_id="kick_ops_kpi",
    trigger_dag_id="nadihaul_ops_kpi",
    conf={"as_of": "{{ ds }}"},
    wait_for_completion=False,
)

# Interview line: “I publish a Dataset (or trigger with conf); consumers shouldn’t hard-wire my task_ids.”

Why. ExternalTaskSensor couples graphs by private task names. Datasets / triggers make the contract the data (or an intentional kick), which survives producer refactors.
